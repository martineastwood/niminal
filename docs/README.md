# niminal docs

Astro Starlight site for niminal.dev.

```sh
npm install
npm run dev
```

- Code on a page comes from `examples/` via `<Example file="x.nml" />`, so it can't drift from the audio.
- `scripts/render-examples.sh` renders the files in `scripts/examples.txt` to `public/audio` (needs `niminal` and ffmpeg). Locally they play from `/audio`; in CI they go to R2 and `PUBLIC_MEDIA_URL` points at `media.niminal.dev`.
- `src/content/docs/reference/opcodes.md` (built-in opcode list) is generated by `niminal docs` before every dev and build, so `niminal` must be on PATH (`cargo install --path crates/niminal-cli`).
- Syntax highlighting reuses `editors/vscode/syntaxes/niminal.tmLanguage.json`.

## Organisation

The sidebar in `astro.config.mjs` is ordered for people using niminal, not for the layout of the repo:

- **Guide** — tasks, in the order you meet them.
- **Language** — the `.nml` file: what the server compiles, then what the sequencer reads, then what both share.
- **niminal (server)**, **nimlive (sequencer)** — one program each: command line, API, editor.
- **Tracker** — the desktop app's manual. It lives here; `tracker/README.md` is build and architecture notes only.

Each section's landing page says which program runs it, and every page in **Language** does, because the server's half and the sequencer's half sit side by side there: **Compiled by niminal**, **Read by nimlive**, or **Read by both programs**. Write from the user's side — what a program does and what you type — not crates, repo modules or internal design. `reference/opcodes.md` is generated, so it carries no such line.

## One-time Cloudflare setup

1. Add niminal.dev to Cloudflare and switch the nameservers at OVH.
2. Create a Pages project named `niminal` and attach niminal.dev as its custom domain.
3. Create an R2 bucket `niminal-media` and attach `media.niminal.dev` as its custom domain.
4. Add repo secrets `CLOUDFLARE_API_TOKEN` (Pages and R2 edit) and `CLOUDFLARE_ACCOUNT_ID`.
