title: Live coding
description: Run a generic sound server and a live sequencer client.

Start the server and a separate `nimlive live` client, then send code from the REPL, the CLI, or the [editor](/reference/editor/). Syntax help and completion come from [`nimlive lsp`](/reference/editor/) and work without a server.

```sh
niminal server
# another terminal:
nimlive live examples/groove.nml
nimlive repl
nimlive send 'chorus.start' --quantize "next 4bars"
```

With a file argument, the live client watches that file and every module it `use`s, and reloads when you save.

## REPL

In the REPL, `:quantize next 4bars` sets when each statement lands (`:quantize off` clears it); `:quit` exits.

Useful live commands once a scene is running (see [Performance](/reference/language/performance/)):

```nml
verse.start
bass.reverse
lead.transpose(+5st)
bass.set(bright: 0.9)
bass.undo
hush
```

## When changes land

Code compiles immediately; sound changes land on a musical boundary. Pass `--quantize` to `send` / `repl`, set `:quantize` in the REPL, or write `@ next 4bars` after a command in source.

Defaults when you omit a quantum: plays on the next cycle, instrument redefinitions on the next beat, most other changes on the next bar. `now` lands as soon as possible.

## Session replay

Every input to a live session is logged by sample (by default under `~/.niminal/sessions/`), so a session replays to identical audio:

```sh
niminal replay ~/.niminal/sessions/<log> --out set.wav
```

Use `--no-log` on the server to skip recording, or `--log PATH` to choose the file. The newest 20 session logs are kept.

## MIDI and OSC

Drive named controls from a controller or OSC sender:

```sh
niminal server
# another terminal:
nimlive live examples/midi_osc.nml --midi --osc-port 9000
```

```nml
ctl cutoff = midi.cc(21).range(200hz..4khz).smooth(10ms)
ctl volume = midi.cc(7).range(-60db..0db)
ctl pan    = osc_in("/fx/pan").range(-60deg..60deg)
```

- `--midi [NAME]` — every MIDI input whose name contains `NAME`, or all inputs if you omit the name.
- `--osc-port PORT` — OSC over UDP on this machine only.

`midi.learn` waits for the next control change and binds to it (the editor can rewrite the line). A clip with `keys: midi.keys(...)` plays from a MIDI keyboard. Details: [Performance](/reference/language/performance/).

## Sending MIDI and OSC out

A `midi_out` is an instrument that plays external gear. Its notes go to a MIDI output port instead of making sound here: a note's `freq` is the key that is pressed (a note name works) and its `gain` the velocity (0db the loudest, -30db the softest), and the note ends when its step does.

```nml
midi_out drums(port: "IAC Driver", channel: 10)
track beat { instrument = drums }
beat.play([c2 ~ d2 c2])
```

`port` is part of the name of an output; if no output matches, the server makes one of that name for other software to listen to. `channel` is from 1 to 16 (1 if left out). The notes go out when the sound card plays them, so the gear stays with the sound here. A render has no sound from a `midi_out` and says so.

A track's signal can be sent over OSC too. `osc_out` passes the signal through and sends its value to an address, as a float:

```nml
track bass {
  instrument = pluck
  out = it.osc_out("/vj/bass", port: 9000)               // this computer, 30 times a second
}
ctl k = 0.5
track knob { out = k.osc_out("/vj/knob", host: "192.168.1.20", port: 9000, rate: 10hz) }
```

A message is sent when the value has changed and `rate` allows it; the first value goes at once. Sending happens whenever the server runs, and is not logged, so a replay does not send.

## Audio input

A track can read the sound card's input with `input(1)`, or `input(1..2)` for two channels:

```nml
track voice { out = input(1).lpf(cutoff: 3khz) }
```

Start the server with `--audio-input` to listen to the default input device (at the output's sample rate). `nimlive render file.nml --input take.wav` plays a WAV file into those tracks instead, for as long as the file lasts unless you say otherwise with `--bars` or `--seconds`.

## Many voices, many cores

The server shares voices among threads. `--render-threads N` sets how many render together, counting the render thread itself (by default your cores, up to 4; `1` renders on one core). Voices are summed in fixed groups of 8, so the sound is bit-for-bit the same whatever the number, and a recorded session still replays to the same bytes.

Groups of voices from tracks that do not depend on each other (no bus or buffer passes between them) are shared out together, so ten tracks of ten voices benefit as much as one track of a hundred. Each track's effect chain still runs on one thread, and a track whose voices write a shared buffer runs its voices one at a time.

Whether sharing a block out is worth it is decided as the music plays: the server times its own voices, and measures what waking its threads costs when it starts. `--render-fork` overrides that: `always`, `never`, or a number of microseconds of work a block must have before it is shared. The sound is the same whichever you choose; only the speed changes.

## Editor

With the [VS Code / Cursor extension](/reference/editor/) connected to a server: **Cmd/Ctrl+Enter** evaluates the block around the cursor, **Cmd/Ctrl+Shift+Enter** the whole file, **Cmd/Ctrl+.** hushes, and the sidebar lists scenes and tracks.
