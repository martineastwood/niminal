# niminal Spec v2

Oct 9, 2026 · @Martin

## Vision

niminal is a modern Csound: a deep audio language for building instruments and processors from scratch, an open score model that any tool can write, and live performance as a fully supported way of working. It runs on an audio engine written in Rust.

**North star:** something BT would have been excited to use on *This Binary Universe*, a through-composed 5.1 album whose opening track was written entirely in Csound, with sound design down to the stutter edit and an electro-orchestral score.

- **Deep:** write DSP from scratch with stateful opcodes, build instruments from them, and generate music in code. Nothing is limited to a fixed menu of primitives.
- **Explicit:** named arguments, typed parameters and units. No positional mystery arguments, no p-fields.
- **Readable at length:** a score for a seven-minute piece stays navigable through sections, functions and a notation suited to each passage.
- **Open score:** the engine understands a score model, not one syntax. niminal's notations, a Python script, a tracker client or a MIDI file all produce it.
- **Live supported:** code can be re-evaluated while playing without glitches, and changes land on musical boundaries.

### Layers

&#91;embedded content: niminal's layers · four front-ends, one score model, one engine\]

The orchestra is the niminal language. The score model is data, so any front-end can write it. The performance layer (tracks, clips and scenes) sits on top for live work, and the engine runs everything, either as a live daemon or as an offline renderer.

### Influences

Csound for the orchestra and score split, the instrument model and user-defined opcodes; Nim for the feel (UFCS, an implicit result value); Swift for labeled arguments; Faust for sample-level DSP; Tidal for pattern transformations; Ableton for tracks, clips and scenes; trackers for row-based writing.

### What we keep from Csound, and what we fix

Keep: instruments as templates with one instance per note, opcodes as composable unit generators, user-defined opcodes, multiple rates, routing between instruments, and a score that any tool can generate.

| Csound | Problem | niminal |
| --- | --- | --- |
| Positional args (`vco2 kamp, kcps, imode…`) | Must memorize argument order | Named args; positional only for an obvious first argument |
| `i`/`k`/`a` variable prefixes | Rate baked into names | Rates inferred; `.init`, `.control`, `.audio` when you need to force one |
| p-fields (`p4`, `p5`) | Anonymous parameters | Typed, named parameters with defaults and units |
| Globals cleared by hand (`gaRev = 0`) | Easy to forget | Buses that clear themselves every block |
| GEN routines by number | Cryptic | Named table constructors such as `harmonics([...])` |
| One opcode per filter design | Inconsistent interfaces | One opcode per job with a `model:` switch |
| Instrument numbers set execution order | Sends arrive a block late | Order sorted from the routing graph |
| Text score, one `i` line per note, generated by external tools | Long and hard to read | An open score model, readable notations and a client library |
| `0dbfs` setting | Classic gotcha | Full scale is always 1.0 |
| Live use added later | Feels bolted on | Quantized, transactional live evaluation in the core |

## Orchestra: syntax and units

The orchestra is written in the niminal language. It looks a little like Nim and Swift, with Csound's model underneath.

```
instr pluck(freq: hz, amp: db = -6db, bright: 0..1 = 0.5) {
  level = env[0 2ms 1 600ms.exp 0]
  osc(saw, freq)
    .lpf(cutoff: freq * (2 + bright * 6), res: 0.3, model: ladder)
    .gain(amp) * level
}
```

### Basics

- **Comments:** `//`.
- **Blocks:** braces, never significant indentation, so evaluating a selected snippet is always safe.
- **Bindings:** no keyword. `name = expr` creates or rebinds a local; reads see the most recent binding above them. Destructuring works: `[l, r] = src`.
- **Rebinding is never feedback:** `sig = sig.lpf(...)` rebinds; feedback is always explicit with `prev(sig)`.
- **Typos are caught by usage:** reading an unbound name is an error; a binding that is never read is a warning.
- **No shadowing of globals:** a local can't share a name with a bus, instrument, track, sample or other top-level declaration.
- **Buses are written only with `+=`.** `out` is the one name that also allows `=`.
- **Named arguments** by default; an obvious first argument may be positional (`osc(saw, freq)`).
- **Method chaining via UFCS:** `x.f(a)` is `f(x, a)`. Opcodes stay freestanding units; the dot is left-to-right wiring.
- **Paren-less calls only after a dot:** `sig.ifft`, `riff.reverse`. A bare name is a reference, never a call.
- **Name resolution after a dot:** a field of the value's type first, then a unit, then an opcode; ambiguity is a compile error.
- **Line continuation:** a line starting with `.` continues the previous expression.
- **Private names:** top-level names starting with `_` are private to their module.
- **No bit-shift operators:** use `shl(x, n)` and `shr(x, n)`.

### Units

Strict units, free rates: anything can be patched into anything, and the scale factor states the meaning, like an attenuverter on a patch cable.

- **Rates never block a connection.** Audio into a control parameter upgrades it to audio rate.
- **Raw signals are unitless** (oscillators, noise, envelopes, LFOs). Unitless × hz = hz; hz + hz = hz; hz + db is an error.
- **Unit suffixes are unit methods:** `800hz` is `800.hz`, and `noise().abs.hz` attaches a unit.
- **Related units convert:** note names to hz, db to linear gain, beats to seconds at the current tempo, semitones applied to a frequency.
- **Unrelated units are an error.** Strip with `.num` to reinterpret deliberately: `(-6db).num.hz`.
- **Bare literals in unit slots are errors** with a quick fix (`cutoff: 800` → "did you mean `800hz`?"). The one exception: gain parameters accept unitless linear factors (`0.5`) as well as decibels, since multiplying by a number is gain.
- **Unit names** are at least two characters and reserved: `sec`, `ms`, `samples`, `hz`, `khz`, `db`, `st`, `deg`, `bpm`, `beat`/`beats`, `bar`/`bars`, plus `%`.
- **Attaching units:** directly to a literal (`440hz`, `4bars`), including rationals (`1/8beat`). Outside brackets a space is fine (`4 bars`). Inside pattern, envelope, line and tracker brackets a space separates steps, so attach the unit or parenthesize: `(1/8 beat)`.
- **Ranges** use `..`: `20hz..20khz`. A range as a parameter type (`bright: 0..1`) declares a bounded unitless parameter.

```
lpf(cutoff: 800hz + osc(sine, 110hz) * 600hz)    // audio-rate modulation
lpf(cutoff: lfo(1/4 beat).range(200hz..4khz))    // mapped range
lpf(cutoff: noise().abs.hz * 8000)               // attach a unit
```

### Rates

Signals run at init (once per note), control (once per block), audio (every sample) or spectral (once per FFT frame) rate. The compiler infers rates. To force one, use a rate method: `x.init`, `x.control`, `x.audio`. A parameter that must be fixed at note start declares it before its type: `length: init sec`.

### Envelopes

Envelopes have their own literal: levels and durations alternate. `env[0 5ms 1 120ms 0.4 | 600ms 0]` starts at 0, takes 5ms to reach 1, 120ms to reach 0.4, holds, and on release takes 600ms to reach 0.

- **Any number of segments;** two levels or two durations in a row is an error.
- **`|` marks the sustain point.** No `|` means a one-shot that plays through.
- **Durations in any time unit, mixed freely.** Beat segments follow tempo changes.
- **Curves are methods on the duration:** `900ms.exp`, `5ms.log`, `600ms.curve(-4)`.
- **Levels can have any unit, as long as they all match:** hz, db or unitless.
- **Releasing mid-segment** starts the release from the current level. `.loop` repeats the shape.
- `adsr(attack:, decay:, sustain:, release:)` is a named-argument shortcut for the same thing.

```
env[0 3ms 1.2 40ms 0.8 200ms 0.6 | 100ms 0.3 2sec 0]   // multi-segment, two-stage release
env[0 4beats.log 1 | 2beats 0]                        // tempo-synced swell
cut = env[200hz 10ms 6khz 300ms.exp 900hz | 400ms 200hz]
wob = env[0 (1/8 beat) 1 (3/8 beat) 0].loop
```

### Control flow

- **`if`/`else` is an expression:** `if it.freq < 2khz { 0db } else { -14db }`.
- **`for` loops run at compile time**, building graph structure or score material. There are no unbounded loops on the audio thread.

```
instr organ(freq: hz) {
  for n in 1..8 {
    out += osc(sine, freq * n).gain(-3db * n)
  }
}
```

## Orchestra: instruments, voices and opcodes

Instruments are templates; each note is a voice. Opcodes are the unit generators voices are built from, and you can write your own.

### Instruments and `out`

An instrument declares typed, named parameters with defaults. Its result is its **last expression**, or **`out`** if the body uses `out`, as with Nim's `result`: `out` starts as silence and can be assigned or added to. Using both in one body is an error. The same rule applies to `opcode` and `fn`. The language has exactly two implicit names: `out` and `it`.

```
instr saw_lead(freq: hz, amp: db = -6db) {
  level = env[0 5ms 1 200ms 0.6 | 300ms 0]
  osc(saw, freq).lpf(cutoff: 2khz).gain(amp) * level     // the last expression is the result
}

instr pad(freq: hz, amp: db = -3db) {
  out  = osc(saw, freq).lpf(cutoff: 1200hz).gain(amp)   // or build up out
  out += osc(sine, freq / 2).gain(amp - 6db)
  // out += noise().hpf(cutoff: 6khz).gain(-24db)
  space += out.gain(-12db)
}
```

- **Each `out +=` line is a layer;** commenting one out mutes it.
- **Instruments return `out`** rather than writing to speakers, so the caller decides where it goes. Calling an instrument or sample inside another instrument gives its audio, as a sub-voice of the enclosing voice.
- **A voice lives until its envelopes finish,** even past its scheduled duration.
- **The compiler warns** if an instrument never writes to `out` or a bus.

### Instrument kinds and voices

| Keyword | A new note… | Used by |
| --- | --- | --- |
| `instr` | Spawns a new voice (poly, the default) | Most instruments |
| `mono` | Updates the one running voice | Bass, leads |

Anything that runs continuously, such as an effect or a generator, is a **track** (see Performance), which adds a mixer, meters, sends and its own stem.

Options go in `with(...)`:

| Option | Effect |
| --- | --- |
| `choke: group` | A new note ends other voices in the group |
| `same_note: release` | A new note releases the previous voice at the same pitch |
| `max: n, steal: oldest` or `quietest` | Caps voices |
| `legato: true` (mono) | Overlapping notes don't retrigger envelopes |
| `priority: last`, `lowest` or `highest` (mono) | Which held note sounds; default last, returning to notes still held |
| `pitch: name` | Which parameter is the pitch (default `freq`) |
| `compensate: false` | Opts out of latency compensation |
| `quantize: 1 beat` | When redefinitions land |

- **Lifetimes:** a voice ends naturally (released and envelopes finished) or forcibly (choked, stolen, replaced), always with a short global fade so it never clicks.
- **Parameters are signals.** In `mono`, a new note updates parameters on the running voice, so glide is ordinary processing: `osc(saw, freq.glide(40ms))`. The same mechanism gives per-note expression (MPE, aftertouch).
- **Pitch:** the parameter named `freq` is the pitch by convention. This is what `same_note`, mono priority, `keys.note` and an unqualified `transpose` act on.
- **No voice limits by default.** A global emergency brake (`config { max_voices: 512 }`) steals the quietest voices and warns. Voice pools grow on a background thread.

### Opcodes (user-defined)

`opcode` defines a unit generator in niminal: it runs in the audio graph, can hold per-voice state between samples, and chains like any built-in. Stateful opcodes run sample by sample, fused into the graph like Csound UDOs with `setksmps 1`, or Faust.

```
opcode one_pole(x, cutoff: hz) {
  state y = 0.0
  a = exp(-2 * pi * cutoff / sample_rate)
  y = x * (1 - a) + y * a
  y
}

opcode drive(x, amount: 0..1 = 0.5) {
  (x * (1 + amount * 9)).tanh
}

out = osc(saw, freq).drive(amount: 0.3).one_pole(cutoff: 800hz)
```

- **The last expression is the output.** `state` declares a variable that persists between samples, per call site and per voice.
- **Multiple outputs** are named and come back as fields:

```
opcode svf(x, cutoff: hz, res: 0..1 = 0.5) -> (low, band, high) { ... }

f = noise().svf(cutoff: 2khz)
out = f.band
```

- **Opcodes can call opcodes**, take trigger inputs, and declare latency, which latency compensation then uses.
- **Rust plugins** implement the same opcode trait, so built-in, niminal and plugin opcodes look identical to the user.

### Functions

`fn` is a plain function that runs at compile or load time: for building structure, helpers and generating score material. It has no audio state.

```
fn fifths(root: note, count: n) {
  for i in 0..count { root + (7st * i) }
}
```

Anonymous functions are `fn(a, b) { a * b }`; `it` covers the one-argument case.

### Scheduling from instruments

An instrument can schedule other notes, the basis of generative writing, as with Csound's `schedule`:

```
instr echo_note(freq: hz, depth: n = 4) {
  out = pluck(freq: freq)
  if depth > 0 {
    schedule(echo_note(freq: freq * 3/2, depth: depth - 1), in: 1/8 beat)
  }
}
```

Scheduled notes go through the score model like any other event, so they are logged, replayable and quantized the same way.

### Parameters: what you pass is what you get

| You pass | Behavior | Example |
| --- | --- | --- |
| Constant | Stays constant | `amp: -6db` |
| Pattern | Each note gets its own value, fixed at note start | `amp: [-6db -12db -9db]` |
| Signal | Stays live; running notes follow it | `amp: lfo(2 beats).range(-12db..0db)` |

### Branching and multichannel

From simplest to most general:

1. **Multichannel expansion:** a comma list in an argument expands across channels: `src.lpf(cutoff: [800hz, 1200hz])`.
2. **`split` with `it`** for asymmetric processing; `it` alone means pass-through.
3. **Named bindings with destructuring** for anything more complex.

```
out = src.split(
  left:  it.lpf(cutoff: 800hz),
  right: it.delay(time: 3/16 beat).hpf(cutoff: 200hz),
)

out = drums.split(dry: it, wet: it.compress(ratio: 8, threshold: -30db)).sum

[l, r] = src
mid  = (l + r) * 0.5
side = ((l - r) * 0.5).gain(+3db)
out  = [mid + side, mid - side]
```

A comma list of signals builds a multichannel signal; the compiler warns when its layout doesn't match the destination, which catches `[pad, bass]` written where a mix (`pad + bass`) was meant.

## Orchestra: routing, delay and space

### Buses

Buses replace Csound's globals. They are declared once, summed automatically and cleared every block.

```
bus space: stereo

instr pluck(freq: hz) {
  out = osc(saw, freq).lpf(cutoff: 900hz)
  space += out.gain(-14db)          // send a copy
}

track room {
  out = space.reverb(room: 0.8, model: plate)
}
```

- **`bus += x` sends a copy** and leaves the original routing alone.
- **`.to(bus)` routes** an output to a bus instead of the master.
- **A track's `out`** goes to the master unless routed with `.to(bus)`.

### Execution order

The compiler builds a dependency graph from bus reads and writes, and sorts it: all writers to a bus run before anything that reads it, within the same block. Buses add no latency, file order is irrelevant, and redefining anything re-sorts the graph. This replaces Csound's numeric instrument order.

**Feedback between buses** has no valid order, so the compiler rejects it and names the loop. Break it explicitly with `prev`, which costs one block (32 samples by default, under 1 ms):

```
track room {
  out = space.reverb(room: 0.85)
  echo += prev(out).gain(-20db)
}
```

Inside a single voice or opcode, feedback can be sample-accurate: `prev(x)` is exactly one sample there.

### Delay lines

- **Simple opcode:** `sig.delay(time: 3/16 beat, feedback: 0.4)`. Beat-based times follow tempo changes.
- **Delay lines as values** replace Csound's `delayr`/`deltap`/`delayw`. A delay line is a bus that remembers: written with `+=`, read with taps.

```
line = delay_line(max: 2sec)
tap1 = line.tap(3/16 beat)
tap2 = line.tap(5/16 beat, interp: cubic)

line += sig + tap1.lpf(cutoff: 3khz).gain(-6db)   // filtered feedback
out = sig + [tap1, tap2]
```

- **Buffer size is known up front:** a literal time sets it; a modulated time requires `max:`. Buffers come from a pre-allocated pool.
- **Short feedback loops** (flangers, Karplus-Strong, combs) are processed per sample automatically.
- **Interpolation is explicit** when modulating: `interp: none`, `linear`, `cubic` or `allpass`.

### Latency compensation

Opcodes with lookahead (limiters, linear-phase EQ, FFT) declare their latency, and the compiler delays parallel paths to keep them aligned, as a DAW does. It is automatic; `with(compensate: false)` opts out.

```
out = drums.split(dry: it, wet: it.limit(ceiling: -1db, lookahead: 5ms)).sum   // dry delayed 5ms
```

### Channel layouts

Every signal carries a channel layout in its type: `mono`, `stereo`, `quad`, `surround(5.1)`, `surround(7.1.4)`, `ambi(order: 3)`, or `ch[N]`. Channel names such as `left` and `center` exist only on layouts that have them.

- **`split` must cover every channel,** or provide `rest:`. Silently dropped channels are an error.
- **`.each(...)`** processes every channel of any layout.
- **Prefer placement over channel names:** `pan(azimuth: 45deg, spread: 0.3)` renders into whatever layout the destination has, so the same code works on headphones, stereo, 5.1 or a speaker ring.
- **The master layout** comes from `config { channels: surround(5.1) }`.
- **Ambisonics is opt-in:** `config { mix: ambi(order: 3) }` makes every bus carry the sound field, decoded at the master to the speakers or to binaural.

| From | To | Default |
| --- | --- | --- |
| mono | any | Centered |
| stereo | surround | Front left and right |
| surround | stereo | Standard downmix coefficients |
| ambisonic | any | Decoded for the master layout |

Override with `config { upmix: ... }` or `.to_layout(...)`; a mismatch shows a one-time notice in the editor.

## Orchestra: data, samples and spectral

### Tables, samples, kits and buffers

All samples are tables, but not all tables are samples, so each has a surface designed for its use.

| Declaration | What it is | Callable |
| --- | --- | --- |
| `table` | Generic, immutable data: wavetables, lookup tables, control curves, impulse responses | No |
| `sample` | Playable audio: a table plus channel layout, loop points, length in beats or BPM, choke group; or a multisampled instrument | Yes, as an instrument |
| `kit` | A folder of samples, addressed by name | Its samples are |
| `buffer` | Writable data; audio buffers play like samples | Audio buffers are |

```
table saw8   = harmonics([1, -1/2, 1/3, -1/4], size: 4096)
table shaper = curve([0 0.2 0.7 1], size: 1024)
table hall   = file("irs/hall.wav")

sample kick  = "drums/kick.wav"
sample hh    = "drums/hh_open.wav" with(choke: hats)
sample amen  = "breaks/amen.wav" with(beats: 4)
sample piano = sfz("keys/piano.sfz")          // key zones, velocity layers, round robins
kit drums    = "drums/808"
```

`kick.data` gives a sample's underlying table, so a recording can serve as a wavetable or impulse response. A kit entry can be a folder of variations, chosen by index (drums\[kick \~ snare.2 \~\]) or patterned with a variation lane on a clip.

### Playing samples

A sample is an instrument whose parameters are its playback settings:

- **`rate:` or `pitch:`** (not both); `start:` and `end:` in time, `%` or beats; `reverse:`; `interp:`.
- **Loops inside a sound:** `loop: 1.2sec..2.8sec`, `loop_mode: none`, `forever` or `sustain`, `crossfade:`; `loop: from_file` reads file metadata.
- **Tempo-synced loops:** `fit: rate` (varispeed), `stretch` (pitch kept, spectral) or `slice` (cut at transients, retriggered on the beat), with `align: bar`. Loop position follows the clock's phase, so live redefinitions never drift.
- **Slices are samples:** `amen.slices(16)` gives callable, patternable pieces for chopping and mashups.
- **Multisampled instruments** (`sfz(...)`, SFZ only to start) choose a zone from the pitch parameter and a layer from `gain`.

```
kick(pitch: -2st)
snare(pitch: +2st).hpf(cutoff: 200hz)
out = amen(fit: slice, align: bar)
piano(freq: c4, gain: -9db)
```

**Engine rules:** samples load off the audio thread and an evaluation lands only once they are loaded; `with(stream: true)` streams long files from disk; sample-rate conversion happens at load; a file's channel count becomes its layout; files are watched and reloaded.

**Live recording** uses buffers: `take.record(input(1..2), when: key("r"), align: bar)`, then `take(loop: forever, align: bar)`.

### Spectral processing

FFT output is a `spectrum` stream with its frame shape in the type (`spectrum[2048, 512]`). Only spectral opcodes accept it, and `.ifft` returns to audio.

```
instr shimmer(freq: hz) {
  out = osc(saw, freq)
    .fft(size: 2048, hop: 512, window: hann)
    .pitch_shift(+12st)
    .blur(time: 300ms)
    .ifft
}

out = src.fft(size: 2048)
  .map_bins(it.gain(if it.freq < 2khz { 0db } else { -14db }))
  .ifft
```

- **Built-ins:** `pitch_shift`, `freeze`, `blur`, `spectral_gate`, `morph`, `cross`, `spectral_mask`, `map_bins` (bins expose `freq`, `mag`, `phase`, `index`).
- **Arrays** are fixed-length (`array[f32, 2048]`) with element-wise math, `.map`, `.sum`, `.max` and indexing. Commas stack and spaces sequence, so `[l, r]` is channels while a frame of bins is data.
- FFT plans are built at compile time; changing FFT size live crossfades between chains.

### Triggers and stutter

Any pattern can become a sample-accurate **trigger signal** with `.trig`, so patterns can drive events inside an effect, not only start voices. `stutter` captures audio continuously and retriggers short slices on each trigger:

```
fills = grid[.... .... ..xx xxxx]

out = drums.stutter(
  on:    fills.trig,
  size:  [(1/16 beat) (1/32 beat) (1/64 beat) (1/128 beat)],
  pitch: env[0st 1beat +12st],
)
```

### Core opcode library (v1)

One opcode per job, with variants as parameters.

| Category | Opcodes |
| --- | --- |
| Oscillators | `osc` with `sine`, `saw`, `square`, `tri`, `pulse(width:)`; `osc(table:)`; `phase_mod:` for FM; `noise` (white, pink or brown) |
| Filters | `lpf`, `hpf`, `bpf`, `notch`, `peak`, `low_shelf`, `high_shelf`; `model:` svf, ladder or biquad |
| Envelopes and modulation | `env[...]`, `adsr`, `lfo`, `glide`, `follow`, `random`, `smooth_random` |
| Delay and reverb | `delay`, `delay_line` and `tap`, `comb`, `allpass`, `reverb` (`model:` freeverb, plate or hall) |
| Dynamics | `compress`, `limit`, `gate` |
| Distortion | `saturate`, `bitcrush`, `waveshape(table)` |
| Granular and time | `grains`, `stutter`, `stretch` |
| Space and mix | `pan`, `width`, `gain`, `xfade`, `sum`, `to_layout` |
| Utility | `range`, `clamp`, `abs`, `prev`, `trig`, `probe`, `print` |
| Spectral | `fft`, `ifft`, `pitch_shift`, `freeze`, `blur`, `spectral_gate`, `morph`, `cross`, `spectral_mask`, `map_bins` |

```
out = piano_take.grains(density: 40, size: 80ms, position: lfo(8 beats).range(0..1), spread: 0.3)
```

## Score model

The engine understands one score model, as data. Every notation and client produces it, just as Csound's score was a simple event format any tool could generate. Keeping the model separate from any syntax is what lets niminal notations, Python, a tracker client and MIDI files all write music for the same orchestra.

### Elements

| Element | Contents |
| --- | --- |
| **Event** | Target (instrument or track), start, duration, named arguments with units, optional id |
| **Lane** | A curve over time for one parameter (`bass.tone`, `tempo`): points with values and curve shapes, or a pattern |
| **Section** | A named, finite container of events and lanes with a length; reusable, transformable and launchable |
| **Arrangement** | Sections placed over time, plus song-level lanes for tempo, meter and automation |

### Time

- **Musical time** (beats and bars, through a tempo and meter map) or **absolute time** (seconds). Both can appear in one score.
- **Positions** read as `bar 5 beat 3`; offsets as `1/8beat` or `250ms`.
- **Tempo and meter are lanes** on the arrangement, so they can change and ramp over a piece.

```
arrangement song {
  sections: [dawn.over(16 bars) build.over(32 bars) theme.over(24 bars) dissolve.over(16 bars)]
  tempo:    env[84bpm (64 bars) 84bpm (8 bars).log 96bpm]
  meter:    [4/4 4/4 7/8 4/4].per_section
  space.width: env[0.2 (88 bars) 1.0]
}
```

### Validation

The daemon checks every event against its target's signature with the same type and unit checker as niminal code. A Python script that passes a gain as a frequency gets the same clear error as a typo in a niminal file, returned as a diagnostic to the client that sent it.

### Updating running notes

An event can carry an id, so later updates reach the running voice: ties, slides and per-note expression. In niminal a scheduled note gives a handle; in JSON an update names the event's "id"; in Python the event object has .set(...). Ids are scoped per launch of a section, and updates to voices that have ended are ignored with a warning.

```
n = pad(freq: c3) for 8beats
at beat 4  n.set(freq: d3)          // the same voice moves to d3
```

### Finite and endless material

- **The score model holds finite material:** events, sections and arrangements with known lengths.
- **Endless patterns** (cycling live material) are niminal values the daemon evaluates itself, producing events as time passes.
- **External clients can still play live** by streaming events slightly ahead of the daemon's clock, with timestamps.

### Wire format

Scores travel as JSON over the protocol (MessagePack later for very large scores) and are saved as `.nms` files. Values keep their units as strings, parsed by the daemon. Every file carries a format version, and there is no separate text form: human-readable notations belong to clients.

```json
{
  "section": "phi", "length": "16bars",
  "events": [
    { "at": "0beat", "dur": "1/4beat", "track": "lead", "args": { "freq": "e4", "gain": "-6db" } },
    { "at": "1/4beat", "dur": "1/4beat", "track": "lead", "args": { "freq": "g4" } }
  ],
  "lanes": [
    { "target": "bass.tone",
      "points": [ { "at": "0beat", "value": "300hz" }, { "at": "4beats", "value": "1.2khz", "curve": "exp" } ] }
  ]
}
```

## Score front-ends

niminal takes events: anything that produces the score model is a front-end, and each client owns its own notation. The language keeps only the notation the daemon has to evaluate itself: mini-notation and grids, for endless live patterns, clip lanes and triggers (plus envelope literals in the orchestra). Through-composed and row-based writing belong to clients, and niminal ships example clients for both.

### Shared symbols

Mini-notation, grids and envelopes share these symbols, and the example clients reuse them, so learning one teaches the others.

| Symbol | Meaning |
| --- | --- |
| Space | One after another in time |
| Comma | At the same time (chords, parallel parts, channels) |
| `~` | Rest, or note off |
| `.` | Nothing new: notes sustain, values hold |
| `x*2` | Repeat within the step |
| `[a [b c]]` | Nested brackets subdivide a step |
| `<a b>` | Alternate one value per cycle |
| `440hz`, `-6db` | Values carry units |

### In the language, and in clients

| Front-end | Where | Best for |
| --- | --- | --- |
| Mini-notation | Language | Loops, live patterns, clip lanes |
| Grid | Language | Drums and triggers |
| Score functions | Language | Passages written once and varied |
| Python | Example client | Generated and algorithmic material |
| Tracker | Example client | Precise multi-track passages |
| Line | Example client | Through-composed melody |
| MIDI import | Example client | Material from other tools |

### Mini-notation

Steps divide one cycle evenly (one bar by default). `[c2 g2 bb2 f2]` is four steps per cycle; `.over(2 bars)` stretches a cycle.

### Grids

Each character is one step; spaces group steps for readability. `x` hit, `X` accent, `o` ghost, `.` rest.

```
hats = grid[x.x. x.x. x.x. x.xX]

groove = grid(drums) {
  kick:  x... x... x... x..x
  snare: .... x... .... x...
  hat:   x.x. x.xX x.x. xxx.
}
```

### Score functions

A section can be a function, so a passage is written once and varied. Score functions build sections from patterns and events; sections from clients mix in freely.

```
fn verse(root: note = c3, energy: 0..1 = 0.5) {
  scene {
    lead: clip { notes: [root+12st ~ root+19st ~], gain: [-12db+energy*9db] }
    bass: clip { notes: [root-12st ~ ~ root-5st] }
  }
}

bridge = load("score/bridge.nms")          // written in a client

song = [intro verse(root: c3) verse(root: f3, energy: 0.8) bridge verse(root: c3, energy: 1)]
```

### Value patterns and event patterns

- **Value patterns** hold notes, numbers or triggers. A note pattern plays on a track that has an instrument, and is an error elsewhere.
- **Event patterns** name their instrument: `pluck(freq: riff)`, or a pattern of samples such as `[kick ~ snare ~]`.
- **On an event pattern,** pattern operations transform the events, universal controls set per-event values, and signal opcodes (`.lpf`) are appended to each voice's output.
- **Patterns in arguments** expand across time, just as comma lists expand across channels: `pluck(freq: [c2 c2 g2 bb2], bright: [0.2 0.8])`. Patterns of different lengths cycle independently.

### Universal controls

Reserved names every event accepts, whatever the instrument:

| Control | Effect |
| --- | --- |
| `pan` | Position of the voice's output |
| `gain` | Level after the instrument |
| `to` | Destination bus |
| `dur` | How long each note is held |
| `nudge` | Small timing offset, for swing and feel |

### Pattern operations

Naming rules: say what it does; keep the accepted term when there is one; one name per thing; settings are named arguments with units; one verb with options over near-identical verbs.

| Tidal | niminal | What it does |
| --- | --- | --- |
| `fast`, `slow` | `fast(2)`, `slow(2)` | Change speed |
| `rev` | `reverse` | Play each cycle backwards |
| `<~`, `~>` | `shift(1/8 beat)` | Move earlier or later |
| `every` | `every(4, it.reverse)` | Change every nth cycle |
| `sometimesBy` | `sometimes(chance: 25%, it.fast(2))` | Change random events |
| `degradeBy` | `thin(20%)` | Randomly drop events |
| `euclid` | `euclid(hits: 5, steps: 8)` | Spread hits evenly |
| `superimpose`, `off` | `layer(after: 1/8 beat, it.transpose(+12st))` | Add a (delayed) transformed copy |
| `jux` | `left_right(it.reverse)` | Original left, changed copy right |
| `struct` | `rhythm(grid[x..x ..x.])` | Play values to a rhythm |
| `ply` | `repeat_each(2)` | Repeat every event |
| `swingBy` | `swing(amount: 20%, every: 1/8 beat)` | Delay every other subdivision |
| `within` | `within(0%..50%, it.fast(2))` | Change part of the cycle |
| `shuffle`, `scramble` | `shuffle(4)`, `pick_random(4)` | Rearrange parts |
| `iter` | `rotate(4)` | Start one part later each cycle |
| `chunk` | `in_turn(4, it.fast(2))` | Change each part in turn |
| `mask` | `mask(grid[x.x. xxxx])` | Silence where the mask is empty |
| `fix` | `where(it.freq < c3, it.gain(-6db))` | Change matching events |
| `segment` | `to_steps(16)` | Turn a signal into steps |
| `chop`, `striate` | `chop(16)`, `interleave_chops(16)` | Cut sample events |
| `linger` | `repeat_start(25%)` | Loop the start of each cycle |
| `inv` | `invert` | Swap hits and rests |

### Composition tools

Deliberate tools for writing, not random generators: `in_scale(minor, root: c3)`, `chord(minor7)`, `arpeggiate(up)`, `voice_lead(...)`, `invert_melody`, `retrograde`, `markov(...)`, `random_walk(...)`, `palindrome`. All randomness is seeded per cycle, so renders are reproducible and code sounds the same live and offline.

### Example clients

niminal ships these as references. Each owns its notation and produces score-model sections, sent over the protocol or saved as `.nms` files and loaded with `load(...)`. Anyone can write others.

**Python.** The `niminal` package builds score-model objects and sends them to a daemon. It covers the whole protocol: loading sections, launching, streaming events, setting ctl values and subscribing to transport. Validation errors come back as exceptions with the same messages as niminal code.

```python
from niminal import Session, Section

phi = Section("phi", length="16bars")
for i, n in enumerate(golden_ratio_melody()):
    phi.event(track="lead", at=f"{i}/4beat", dur="1/4beat", freq=n, gain="-6db")

s = Session("ws://localhost:7400")
s.load(phi)
s.launch("phi", at="next bar")
```

**Tracker.** Row-based writing, standalone or as a VS Code mode. Rows are time, `step` apart; columns are lanes named in the header (a track's notes, an instrument or track parameter, or a universal control), so there are no hex effect codes.

```
// intro.nmt
step: 1/4beat
//   lead.notes   lead.gain   bass.notes   bass.tone   perc.notes
00   e4           -6db        e2           300hz>      kick
01   .            .           .            .           hh
02   g4           .           .            .           snare
03   .            .           ~            1.2khz      hh
04   a4*2         -9db        b1           .           kick
05   .            .           .            .           hh
06   [e4,g4,b4]   -3db        .            400hz       snare
07   ~            .           .            .           [kick,hh]
```

- Repeat a column (two `lead.notes`) for more voices.
- `300hz>` slides from this value to the next one in its column.
- Cells accept expressions without spaces (`root+12st`).
- The editor aligns columns, moves between cells with Tab, advances a row on step entry, and highlights the playhead row.

**Line.** Through-composed writing: values and durations alternate, chords stack with commas, rests take a duration, lanes attach as curves, and articulations (ties, legato, staccato, accents) mark individual notes.

```
// theme.line
track: keys
e4 1beat   g4 (1/2 beat)   a4 (1/2 beat)   b4 2beats
~ 1beat    [e4, g4, b4] 3beats
d5 (3/2 beat)   c5 (1/2 beat)   b4 4beats
gain: env[-18db 6beats -6db 6beats -12db]
```

**MIDI import.** Standard MIDI files become sections, with channels mapped to tracks and controllers mapped to lanes.

## Performance

The performance layer organizes playing live the way Ableton's session view does: tracks persist, clips come and go on them, scenes launch sets of clips. The same tracks, clips and scenes are what an arrangement sequences, so live work and finished pieces share one structure.

### Tracks

A track has parameters, a default instrument, note effects, audio effects, sends and a mixer. In each stage, `it` is that stage's input: incoming events for `notes`, the summed voices for `out`.

```
track bass(tone: hz = 2khz) {
  instrument = pluck(bright: 0.4)
  notes      = it.thin(10%)                 // note effects, applied to every clip
  out        = it.drive(amount: 0.2).lpf(cutoff: tone)
  space     += out.gain(-14db)              // send
}
```

- **A track with an instrument plays plain note patterns,** like a MIDI clip on an instrument track.
- **Tracks are created on first use** with no effects, so quick ideas need no declaration.
- **Mixer:** `gain`, `pan`, `mute`, `solo`; `with(quantize: ...)` sets launch quantization.
- **Re-evaluating a track** carries its effects' state over, without clicks.

### Clips

A clip is a section for one track: a bundle of **lanes** sharing one timeline.

```
clip riff {
  length: 2 bars
  notes:  [c2 ~ eb2 g1 ~ c2 bb1 ~]
  gain:   [0db -6db -3db -9db]
  bright: [0.2 0.5 0.8]
  tone:   env[400hz (2 bars).exp 3khz]       // clip envelope on a track parameter
}
```

- **Lane targets:** `notes` (pitch, or samples for drum clips), instrument parameters, track parameters, and universal controls. An unknown lane name is an error. Lanes target only their own track, so clips stay portable; scene and arrangement lanes can target any track.
- **Step lanes** are read when each note starts and cycle at their own length (polymeter); `.per_note` gives the nth note the nth value instead.
- **Envelope and signal lanes** run on the clip's timeline, restart on launch and loop with it.
- **`length:`** defaults to one cycle.
- **Shorthand:** `[c2 ~ eb2]` means `clip { notes: [c2 ~ eb2] }`, and a section loaded from a client (`load("score/riff.nms")`) is a clip too.
- **Lanes are fields,** so clips can be changed lane by lane: `riff.set(bright: [0.9])`, `riff.set(gain: riff.gain.reverse)`.

### Scenes

A scene is a named set of clips, one per track, launched together. An arrangement is scenes (or other sections) over time.

```
scene verse  { bass: riff, drums: groove, keys: ~ }      // ~ stops that track
scene chorus { bass: riff.transpose(+5st), drums: groove, keys: chords }

launch chorus @ next 4 bars
```

### Live commands

```
play bass = riff                 // launch a clip on a track
play bass = riff.fast(2)         // swap it at the track's next cycle
mute drums @ next bar
solo bass
unsolo
stop keys
hush                             // stop all tracks gracefully
panic                            // emergency stop: silence within one block
```

**Bindings are reactive:** re-evaluating `riff = ...` updates every track playing it, each at its own quantize point, without touching the `play` line.

### Quantized changes

Every change lands on a musical boundary. Code compiles immediately; the result waits. The quantum is set at four levels, most specific first: per evaluation (`@ next 4 bars`, or the editor's "now" shortcut), per definition (`with(quantize: 1 beat)`), per kind in `config`, and a global default.

```
config {
  quantize: {
    default: 1 bar
    play:    cycle      // each track's clip cycle
    instr:   1 beat     // instrument redefinitions
    track:   1 bar      // track redefinitions
    ctl:     now
    tempo:   1 bar
  }
}

tempo 124bpm @ next bar over 2 bars
```

- **Boundaries:** `now`, `beat`, `bar`, `N beats`, `N bars`, `cycle`. `@ next 4 bars` aligns to the 4-bar grid; `@ in 4 bars` counts from now.
- **One evaluation is one transaction:** all its changes land together, at the coarsest boundary among them.
- **Last write wins** for pending changes; the editor can cancel them and shows a countdown.
- **Missed boundaries** (slow compile or sample loading) land on the next one, and the editor says so.

### Live coding model

- **Evaluation modes:** the block or line under the cursor while performing; the whole file when rendering.
- **Transactional:** code that fails to compile changes nothing, and playback continues.
- **Redefinition:** new notes use a new instrument definition; sounding notes finish on the old one.
- **State carry-over:** tracks and their effects keep filter memory and delay lines across edits.

### External control

A `ctl` is a named control value fed by code, MIDI, OSC or a modulator; one `ctl` driving several parameters is a macro.

```
ctl filth  = midi.cc(21)
ctl volume = midi.cc(7).range(-60db..0db)
ctl width  = osc_in("/fx/width").range(0..1)
ctl drive  = 0.3                                  // set from code; re-evaluating glides

track bass { out = it.lpf(cutoff: filth.range(200hz..4khz)).drive(amount: filth) }
```

- **Units come from the mapping;** hardware controls are lightly smoothed by default (`.smooth(0ms)` turns it off); `midi.learn` binds to the next control moved and rewrites itself to the actual CC.
- **Keyboards** are live value patterns with fields, with per-note pressure as a signal (MPE):

```
keys = midi.keys(channel: 1)
play live = pluck(freq: keys.note, amp: keys.velocity.range(-30db..0db), bright: keys.pressure)
```

- **Triggers:** `key("r")` from a connected client, MIDI notes and `osc_in` messages.
- **Audio inputs:** `input(1)` or `input(1..2)`; layout follows the channel count.
- **Live clients** (Python or anything else) play by streaming timestamped events slightly ahead of the daemon's clock.

## Engine and architecture

Client/server. The daemon owns the session and does all compilation; clients are thin and only send messages, so they can run anywhere, including an iOS app controlling a more powerful machine. Live and offline share the same crates, so they sound identical.

### Components

| Crate | Responsibility |
| --- | --- |
| `niminal-lang` | Parser, type and unit checker, desugaring to a dataflow graph and to the score model |
| `niminal-score` | The score model: events, lanes, sections, arrangements, JSON and `.nms` files |
| `niminal-engine` | DSP runtime: graph execution, opcodes, voice pools, buses |
| `niminal-daemon` | Session, clock, audio device, protocol, file watching, evaluation log |
| `niminal-lsp` | Language server: diagnostics, autocomplete, hover docs |
| `niminal-cli` | `niminal daemon`, `niminal render`, `niminal lsp` |
| `niminal` (Python) | Client library for the score model and the protocol |

Rust for the engine, compiler and daemon: no garbage collector, so the audio thread never pauses. Clients can be written in anything; Kotlin with Compose Multiplatform suits a later desktop and mobile UI. niminal is self-contained for now: it doesn't host VST3 or CLAP plugins.

### Protocol

- **JSON-RPC 2.0 over WebSocket.** Requests and responses are paired by id; the server pushes notifications. A handshake carries the protocol version.
- **Messages:** `eval` (source, file, range, quantize override; replies "lands at bar N" or diagnostics, then a `landed` notification), `score.load`, `launch`, `event.stream`, `event.update`, `cancel`, `hush`, `panic`, `subscribe` (transport, pending changes, voices, CPU, meters, probes), `file.put`.
- **Later:** a binary channel for meters, scopes and spectra.
- **OSC is an input surface,** not the client protocol: it feeds `ctl` values and a few commands for controllers like TouchOSC.

### Remote use and files

- **Localhost by default;** remote connections require a token and TLS.
- **Paths resolve on the daemon's machine,** relative to the project root. Evaluation can only read the project and configured library folders; remote clients upload files with `file.put`.
- **Audio plays on the daemon's machine.** Several clients can share one session; last write wins per name.

### Engine pipeline

1. Parse and type-check (units, rates, named arguments) off the audio thread.
2. Desugar chains, `split`, multichannel expansion, patterns and notations into a dataflow graph and score events.
3. Diff against the running graph to carry node state across.
4. Hold the result until its quantize boundary, then swap it in lock-free.
5. Process audio in blocks, with events timestamped inside a block for sample accuracy; stateful opcodes and short feedback loops run per sample, fused into one loop per region. They start as compiled Rust closures over an intermediate representation that a Cranelift JIT could compile later; SIMD across voices comes later still.

- **No allocation on the audio thread;** voice pools grow on a background thread.
- **Opcodes are a Rust trait** with named, typed ports and declared latency. It drives type checking, autocomplete, generated documentation and the plugin API.
- **No OS-specific code in the engine,** so it can compile to WebAssembly for a browser playground. A WebAssembly build runs in CI from day one; the playground itself comes after v1.

### Rendering

```
niminal render main.nml song --out song.wav
niminal render main.nml song --from "bar 64" --to "bar 80"     // iterate on a passage
niminal render main.nml song --stems --out stems/               // one file per track and bus
niminal render --replay set.log --out set.wav                   // re-render a live set
```

- **Length:** the arrangement's length, plus a tail that ends when the master stays below -90db for one second (`--tail` overrides).
- **Freeze:** `freeze lead` renders a heavy track to a buffer and plays that, to save CPU; `unfreeze lead` restores it.
- **Replay:** the evaluation log records evaluations and all external input (MIDI, OSC, `ctl`, keys, optionally audio), so a live set re-renders exactly, deterministically. After v1, capture last 32 bars as jam will turn the log into an editable arrangement saved as .nms.

### Modules and namespaces

A module is a file. `use rig` loads `rig.nml` from next to the current file, then the project library, then installed packages.

- **The core library is always in scope.** `use` imports a module's names unqualified; `as` gives it an alias; `::` qualifies a name only on collision.
- **Everything top-level is visible** except names starting with `_`. Using a module starts its tracks. A module loads once; circular `use` is an error.
- **One `config` per project.** Imported files are watched and re-evaluated as a whole on save, transactionally.

```
use rig
use score/verse
use acme_verbs as av

out = sig.av::shimmer(size: 0.9)
```

### Safety

Always on, because live mistakes shouldn't hurt ears or speakers.

- **NaN and infinity:** an offending voice is silenced and reported.
- **DC blocking** and a **master limiter** at -0.3db true peak (`config { safety: { ceiling: -0.3db } }`); the limiter can be disabled only for offline renders.
- **`panic`** silences everything within one block, stops all voices and clears delay lines; bound to an editor shortcut.
- **Runaway feedback** on a bus is flagged.

### Debugging

- **`.probe("name")`** passes a signal through and streams it to the editor as a scope and meter.
- **`print(x)`** shows a control value in the editor.
- **Every bus and track has a meter;** `solo` isolates a track.

### Sync and output

Ableton Link and MIDI clock in and out; `midi_out(port:, channel:)` is an instrument that plays external gear; `osc_out(...)` sends values.

### First client: VS Code

Cmd+Enter sends the block under the cursor, Shift+Cmd+Enter sends it unquantized; inline diagnostics, countdowns on pending code, a flash when it lands, a tracker editing mode, and a status bar with bar:beat, tempo, CPU and voices. It starts `niminal lsp` for autocomplete and docs.

### A basic synth

```
instr saw_lead(freq: hz, amp: db = -6db) {
  level = env[0 5ms 1 200ms 0.6 | 300ms 0]
  osc(saw, freq)
    .lpf(cutoff: 2khz, res: 0.2)
    .gain(amp) * level
}

saw_lead(freq: a3) for 1beat
```

### A filter that follows the note

The cutoff is relative to `freq`, so high notes stay as bright as low ones, and a fast envelope adds a pluck.

```
instr pluck(freq: hz, amp: db = -6db, bright: 0..1 = 0.5) {
  level = env[0 2ms 1 600ms.exp 0]
  sweep = env[0 1ms 1 250ms.exp 0]
  cutoff = freq * (2 + bright * 6) + sweep * freq * 8
  osc(saw, freq)
    .lpf(cutoff: cutoff.clamp(20hz..18khz), res: 0.3, model: ladder)
    .gain(amp) * level
}
```

### Opcodes from scratch

```
opcode dc_block(x) {
  state x1 = 0.0
  state y1 = 0.0
  y = x - x1 + 0.995 * y1
  x1 = x
  y1 = y
  y
}

opcode fold(x, amount: 0..1 = 0.5) {
  (x * (1 + amount * 8)).sin
}

instr folded(freq: hz) {
  out = osc(sine, freq).fold(amount: env[0 2sec 1 2sec 0]).dc_block
}
```

### BT-style: a 5.1 passage

A granular piano cloud circling the room, a through-composed theme, and stuttered drums, arranged with a tempo ramp.

```
config { channels: surround(5.1) }

sample piano_take = "recordings/piano_phrase.wav"
sample piano      = sfz("keys/piano.sfz")
kit glitch        = "drums/glitch"
theme             = load("score/theme.nms")      // from the line client

bus hall: surround(5.1)
track room { out = hall.reverb(room: 0.9, model: hall) }

track keys {
  instrument = piano
  out = it.pan(azimuth: lfo(16 beats).range(-120deg..120deg), spread: 0.4)
  hall += out.gain(-10db)
}

track cloud(level: db = -60db) {
  out = piano_take
    .grains(density: 30, size: 120ms, position: lfo(32 beats).range(0..1), spread: 0.6)
    .pan(azimuth: lfo(24 beats).range(0deg..360deg))
    .gain(level)
  hall += out.gain(-6db)
}

fills = grid[.... .... .... ..xx]

track beat {
  out = it.stutter(
    on:    fills.trig,
    size:  [(1/16 beat) (1/32 beat) (1/64 beat) (1/128 beat)],
    pitch: env[0st 1beat +12st],
  )
}

groove = glitch[kick ~ ~ kick ~ snare ~ ~]

scene dawn      { keys: theme.slow(2), beat: ~ }
scene awakening { keys: theme, beat: groove }
scene dissolve  { keys: theme.retrograde.slow(4), beat: groove.thin(60%) }

arrangement binary {
  sections:    [dawn.over(16 bars) awakening.over(32 bars) dissolve.over(16 bars)]
  tempo:       env[84bpm (40 bars) 84bpm (8 bars).log 92bpm]
  cloud.level: env[-60db (16 bars) -12db (32 bars) -12db (16 bars) -60db]
}
```

Rendered with `niminal render binary.nml binary --stems --out stems/`, or launched scene by scene live.

### A section generated in Python

```python
from niminal import Session, Section

fib = [1, 1, 2, 3, 5, 8, 13, 21]
phi = Section("phi", length="8bars")
t = 0
for n in fib:
    phi.event(track="keys", at=f"{t}/4beat", dur=f"{n}/8beat", freq=f"c4+{n}st", gain="-9db")
    t += n

Session("ws://localhost:7400").load(phi)
```

## Open questions

The design history and earlier decisions live in the v1 doc. These are new to v2, or left for dogfooding.

- [x] **Score file format:** decided. JSON `.nms` with a version field; no separate text form, since clients own human-readable notations.
- [x] **Event ids:** decided. Handles in niminal (`n.set(...)`), `"id"` fields in JSON, objects in Python; ids are scoped per launch of a section; updates to ended voices are ignored with a warning.
- [x] **Stateful opcode performance:** direction decided. Block processing for stateless opcodes, fused per-sample loops for stateful chains, compiled Rust closures first with an IR a Cranelift JIT could compile later; SIMD across voices later. Details settled by benchmarks.
- [x] **Plugin hosting:** decided. Self-contained for now; no VST3 or CLAP hosting.
- [x] **Multisample formats:** decided. SFZ only to start.
- [x] **Line client articulations:** decided, yes. Ties, legato, staccato and accents are part of the line format.
- [x] **Tracker client slide marker:** decided. Keep `300hz>`; the client can change it independently.
- [x] **Clip lanes:** decided. Keep `.per_note`; lanes target only their own track, and scene and arrangement lanes handle other tracks.
- [x] **Capture:** decided, after v1. `capture last 32 bars as jam` builds an editable arrangement from the evaluation log and saves it as `.nms`.
- [x] **Python client scope:** decided. Full protocol: loading, launching, streaming, `ctl` values and transport.
- [x] **Numbered sample variations:** decided. Field syntax (`snare.2`) on kit entries that are folders, plus a `variation` lane on clips.
- [x] **Browser playground:** decided. After v1, with a WebAssembly engine build in CI from day one.
